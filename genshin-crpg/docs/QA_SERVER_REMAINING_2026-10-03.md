## 외부 SQLite 쓰기 잠금: 조건부 위험 유지

기존 별도 프로세스 검사에서 외부 `BEGIN IMMEDIATE`가 같은 DB의 쓰기 잠금을 5초 넘게 잡으면 게임 행동은 약 5,013ms 뒤 실패했고, 그 사이 요청한 health도 약 4,913ms 지연됐다. `DatabaseSync`의 `busy_timeout=5000` 대기가 Node 이벤트 루프 전체를 막기 때문이다. 잠금 해제 후 같은 requestId 재시도는 1회만 반영됐으며 영수증·revision·계정 큐·트랜잭션 누수는 없었다. 이번에는 이 부하 검사를 반복하지 않고 실행 경로를 다시 확인했다.

| 경로 | 같은 서비스 DB에 별도 쓰기 잠금을 잡는가 |
|---|---|
| `tools/install-fixed-region-test-release.sh` | 설치 파일·심볼릭 링크를 바꾸고 동일 systemd 서비스를 재시작한다. 설치기 자체는 DB를 쓰지 않는다. `flock`은 설치기 중복 실행 방지이며 모든 임의 Node 프로세스를 막는 DB 잠금은 아니다. |
| `tools/promote-test-release-to-production.sh:64` 백업 | 원본을 `readOnly:true`로 열고 `VACUUM INTO`로 별도 백업 파일을 만든다. 원본 DB에 쓰는 백업이 아니다. |
| `tools/prepare-seoul-production.sh` / `tools/promote-seoul-production.mjs` | 기존 운영 DB/WAL/SHM을 덮어쓰지 않는다. 원본은 읽기 전용, 새 대상 DB에 쓰며 기본 테스트·운영 DB 경로도 다르다. |
| 웹 운영자 도구 | 현재 서비스와 동일한 `store.db` 연결을 사용한다. 별도 프로세스의 장기 writer는 아니다. |
| 수동 SQLite 편집, 별도 Node 중복 실행, 잘못된 동일 DB 경로 설정 | 서비스 밖의 writer가 될 수 있다. 서버 생성자에는 같은 DB를 여는 다른 프로세스를 배제하는 전용 프로세스 잠금이 없다. 같은 포트의 중복 실행은 운영체제가 막지만 다른 포트는 별개다. |

정상 도구의 경로를 확인했을 뿐 실제 VPS 환경 파일·실행 프로세스·디스크 상태는 읽지 않았다. 실제 환경에서 테스트·운영 DB가 분리돼 있는지는 사용자 측 운영 점검 사항이다. SQLite timeout을 임의로 줄이거나 늘리기, 비동기 DB 구조 변경, 응답을 받지 못한 변경 요청의 무조건 재전송은 적용하지 않았다.

영구 기록은 장기 디스크 용량 계획이 필요하지만 보유 기한이 정해졌다는 근거는 없다. 이번에 삭제하지 않았다. 다른 배포용 `server/worker.mjs`의 영수증 정리 규칙을 서울 Node 서버에도 적용된 것으로 혼동하지 않는다.

추가 읽기 전용 `EXPLAIN QUERY PLAN`에서 일반 replay 조회는 `(account_id, request_id)` 기본키 인덱스를 사용했다. 운영자 화면의 최근 영수증 30개 조회는 `account_id`로 찾은 뒤 `USE TEMP B-TREE FOR ORDER BY`를 사용한다. 따라서 `LIMIT 30`이 계정의 과거 영수증 전체를 전혀 읽지 않는다는 뜻은 아니다. 실제 대규모 기록으로 지연을 측정하지 않았으므로 성능 결함으로 확정하거나 인덱스를 추가하지 않았다.

## 캐시와 긴 연결의 남은 메모리 경계

- 메인 Runtime은 최대 16개다. `lastUsed`는 갱신하지만 유휴 시간만으로 삭제하는 timer는 없다.
- 공개 프로필은 전체 Runtime 대신 공개 DTO 최대 24개를 보유한다. revision·월 변경·저장 invalidate로 다시 만들며, 목록 수와 갱신 규칙을 시간 기반 메모리 반납으로 오해하지 않는다.
- 훈장 캐시는 60초 내 값을 재사용하고 만료 후 조회 시 갱신한다. 모든 만료 항목을 주기적으로 제거하거나 전체 항목 수를 제한하지는 않는다. 계정의 저장 invalidate/삭제 시 해당 항목은 제거된다. 조회한 계정 수에 따른 보유량은 별도 장기 관찰 대상이다.
- 공개 ID 캐시는 이번 수정 후 재구축 당시 존재하는 계정만 유지한다. 현재 계정 수 자체를 상수로 제한하는 캐시는 아니다. 삭제 직후 모든 항목이 즉시 사라지는 것도 아니며 해당 ID 조회 또는 다음 재구축 때 제거된다.
- SSE는 전체 500개·계정별 8개, 연결별 대기 데이터 128KiB, drain 없이 30초 대기 시 종료하는 기존 제한을 유지한다. 500 × 128KiB = 62.5MiB는 대기 payload 제한을 합한 값일 뿐 소켓·HTTP·JS 객체·Runtime·SQLite·OS 메모리를 포함한 서버 전체 한도가 아니다.

앞선 25개 저장·100 SSE 혼합 검사와 명시적 GC 비교는 유효한 단기 관찰이다. 실행 조건에 따라 RSS가 크게 달랐으므로 VPS의 RAM 용량 보장으로 환산하지 않는다. 이번에는 24시간/7일/수주 지속 연결, 실제 네트워크 단절, 실 VPS의 메모리·디스크 압박, 수십만 영수증 운영자 조회를 실행하지 않았다.
