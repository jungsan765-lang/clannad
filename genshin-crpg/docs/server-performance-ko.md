# 서버 지연 종합 분석 및 구현 보고

기준 main: `abe662b5940763ef17b81c7392b33f49dd5c65d3`, 게임 0.14.5.
구현 브랜치: `perf/crpg-durable-state-v0145`.
운영 Worker·D1·기존 세이브는 변경하지 않았습니다. 한국 실측 전이므로 최종 PR과 운영 배포는 보류 상태입니다.

## 쉽게 설명하면

현재는 이동 한 번 할 때마다 큰 세이브를 멀리 있는 공용 저장소로 보내고 확인을 기다립니다. 이미 읽어 둔 세이브를 재사용해도, 쓰기 확인을 기다리는 시간이 대부분 남습니다.

새 구조는 각 계정 바로 옆에 전용 저장 공간을 둡니다. 거기서 로그인 상태 확인, 게임 계산, 저장 완료까지 끝낸 뒤 응답합니다. 공용 D1에는 계정·랭킹과 추가 백업을 남깁니다. 저장을 생략해서 빠르게 보이는 방식이 아닙니다.

## 운영 관측치에서 확인되는 병목

| 행동 | 전체 | 저장 대기 | 전체 중 저장 | 인증 등 사전 처리 |
|---|---:|---:|---:|---:|
| STORY_READ | 2,674ms | 1,709ms | 63.9% | 241ms |
| STORY_PAUSE_FREE | 1,724ms | 1,476ms | 85.6% | 248ms |
| MOVE | 1,825ms | 1,573ms | 86.2% | 252ms |

사용자 제공 개별 로그이며 평균·p95 수치는 아닙니다. MOVE에서 세이브 읽기는 이미 캐시 적중으로 0ms입니다. SQL 계산 자체 0.1~1ms와, Worker가 저장 응답을 받기까지 1.5초 이상 걸리는 것은 다른 측정입니다. 또한 Workers의 시계는 I/O 사이에 고정될 수 있어 engine/serialize 0ms를 CPU 비용이 없다는 뜻으로 읽으면 안 됩니다.

코드상 행동 확정 batch에는 이전 전체 state의 백업과 새 전체 state의 갱신, receipt 기록, 필요 시 랭킹 갱신이 있습니다. 378KB state라면 백업+새 state만 원시 문자열 기준 약 756KB를 전달합니다. JSON 이스케이프·receipt·프로토콜 오버헤드는 별도입니다. 실제 네트워크 캡처로 측정한 바이트 수는 아닙니다. 매 3 revision 정리 작업도 별도로 있습니다. 매 action 인증/빈도 확인 D1 경로도 남아 있습니다.

검토 범위는 Worker 라우팅·세션·핫 캐시·공유 엔진, DB 스키마와 백업/receipt, 클라이언트 pending journal·읽기 journal·재접속·revision 충돌·응답 설치, 전투·난수·이동·생활/작업·스토리 체크포인트, 빌드 해시와 Pages workflow입니다.

## 대안 비교와 선택

| 방법 | 해결하는 것 | 남는 문제 | 판단 |
|---|---|---|---|
| 전체 JSON을 D1에 계속 저장 | 기존 구조 유지 | 매번 큰 백업/갱신과 원격 확정 대기 | 목표에 부적합 |
| D1 gzip/BLOB | 전송량과 저장량 감소 | 압축 비용과 원격 확정 대기는 유지 | 추가 백업에 채택 |
| D1 state 분할 | 안 바뀐 큰 필드 재쓰기 감소 | 인증·commit의 원격 왕복은 유지 | 주 구조로 선택하지 않음 |
| 행동 저장을 메모리에서 모아서 나중에 쓰기 | 즉시 응답 가능 | 승인된 전투·보상·난수 결과 유실 가능 | 사용하지 않음 |
| 계정별 SQLite DO | 인증·순서 제어·저장 확정을 한곳에서 처리 | 이전/복구 구현, 랭킹 지연, 지역·비용 검증 필요 | 채택 |

state는 최상위 값과 그 아래 한 단계 필드로 손실 없이 나눕니다. 자주 바뀌는 global 값과 큰 인벤토리 등의 변경 여부를 따로 비교해 바뀐 조각만 씁니다. 큰 배열은 저장상 하나의 조각이므로 전투 로그가 큰 경우 약 348KB를 로컬 SQLite에 다시 쓸 수도 있습니다. 응답에서는 배열의 추가·삭제 부분만 전송합니다. 실제 운영 378KB 세이브의 내부 구성은 제공받지 못했으므로, 어느 필드가 몇 %인지 만들어 내지 않았습니다.

동기 확정 대상은 이동·전투·보상·아이템/장비·작업 시작/완료 등입니다. 결과·난수·revision·requestId receipt·최근 복구 정보·추가 백업 예약을 원자적으로 기록하고 저장 확인 후 응답합니다. 같은 요청 재전송은 결과 조회가 되며, 동일 requestId를 다른 내용에 재사용하면 거부합니다. 다른 기기의 오래된 revision도 거부합니다. 순수 메뉴와 기존 대화 묶음 정책은 그대로 유지합니다.

새 세션은 무작위 비밀값에 계정 주소만 붙입니다. 계정 주소를 안다고 로그인할 수 없습니다. 비밀값 해시·만료·로그아웃 취소 여부를 계정 DO에서 매번 확인하므로 정상 행동 중 D1 인증 조회는 0회입니다. 로그아웃을 D1에 반영하는 데 실패해도 취소된 토큰을 되살리지 않습니다.

작은 응답은 클라이언트가 지원한다고 요청한 경우에만 사용합니다. 확인된 서버 revision의 별도 복사본에 적용하므로 사용자가 미리 읽은 대사나 메뉴 상태와 섞이지 않습니다. 기준이 다르면 같은 requestId로 전체 응답을 다시 받아 복구합니다. 난수 상태는 클라이언트에 공개하지 않습니다. 기존 UI에는 전체 응답을 보내 호환성을 유지합니다.

## 실제 로컬 실행 환경 벤치마크

Node 모의 저장소뿐 아니라 Cloudflare `workerd`와 실제 로컬 SQLite DO로 측정했습니다. HTTP 요청부터 JSON 응답 다운로드까지 측정하고, 각 항목 30회·초기 2회 제외, 시험 상태 초기화는 측정 밖에서 수행했습니다. 운영 세이브 대신 실제 엔진으로 만든 합성 세이브를 사용했습니다. 인터넷 왕복과 Cloudflare 운영 복제 지연은 포함하지 않습니다.

| 시나리오 | state | 중앙값 | p95 | 응답 |
|---|---:|---:|---:|---:|
| 일반 MOVE | 32.7KB | 10.3ms | 14.3ms | 1.43KB |
| 장비가 많은 MOVE | 378.1KB | 19.5ms | 28.4ms | 1.43KB |
| 장비가 많은 COMBAT | 381.0KB | 22.2ms | 30.0ms | 7.70KB |
| 전투 기록이 큰 COMBAT | 378.6KB | 20.7ms | 26.6ms | 7.59KB |

최종 측정 구현 식별자: `server-12121bec8a3c97c37b82`. 원시 샘플은 `reports/server-v2/latency-local.json`에 있습니다. 전체 379KB 응답과 비교하면 시험 MOVE 응답은 약 99.6%, COMBAT 응답은 약 98.0% 작습니다. 실제 전투와 세이브 구성에 따라 달라집니다.

압축 비교에서 합성 378,100바이트 JSON은 gzip 16,736바이트로 약 95.6% 줄었습니다. 반복 장비가 많은 합성 자료이므로 실제 운영 압축률이라고 볼 수 없습니다. 로컬 D1 실험 중앙값은 작은 쓰기 9.7ms, 전체 JSON 11.0ms, gzip 12.1ms였습니다. 원격 지연이 없는 환경에서는 압축 CPU 비용 때문에 더 느릴 수도 있다는 결과입니다.

**D1을 계속 썼을 때 한국에서 얻을 수 있는 최저 지연은 아직 확정할 수 없습니다.** APAC/HKG 배치와 SQL meta만으로 그 수치를 계산할 수 없습니다. 제공된 prelude 250ms도 작은 쓰기의 보장된 하한은 아닙니다. 별도 원격 시험 D1에 19바이트/전체 JSON/gzip을 각각 써서 바인딩 왕복·SQL 시간·전체 응답 시간을 함께 측정하도록 준비했습니다.

한국 목표는 따뜻한 MOVE/COMBAT 중앙값 150ms 이하, p95 300ms 이하입니다. 현재 환경에는 사용자의 Cloudflare 배포 인증과 한국 접속 경로가 없으므로 이 목표를 통과했다고 주장하지 않습니다. 장시간 유휴 후 cold start, 실제 운영 세이브, 동시 사용자 부하도 운영 승격 전 확인할 항목입니다. Node 기반 브라우저 시험에서 cold 엔진 생성에 약 150~250ms가 관측되어, cold start가 공짜라고 보지 않습니다.

## 회귀·복구 검증

전체 release gate는 43개 스크립트입니다. 구 버전 0.13.43 세이브 8종(두 루트의 대화·출발·전투·시간제 작업)도 검증합니다. 소스 UI와 빌드된 UI 각각을 D1/DO 두 경로로 Chromium에서 검사했습니다. 느린 응답·응답 유실·새로고침·대사 묶음·단일 선택·33단계 장면·전투 HP/연출까지 포함합니다.

추가 DO 검사에는 동시 중복/서로 다른 요청, 영수증 재조회, revision 충돌, SQLite 트랜잭션 실패, 확정 직후 응답 유실, 객체 재시작, 인증 취소/만료, 이전 중 실패, 활성화 후 객체 분실 차단, 원본 보호 트리거, D1 장애 중 행동 계속, 압축 사본과 checksum, drain 후 최신 세이브/영수증 복귀가 포함됩니다. 최종 결과와 실행 범위는 `reports/server-v2/validation.json`을 확인합니다.

Wrangler dry-run으로 빌드와 DO 바인딩을 확인했습니다. 실제 Cloudflare staging 배포와 Windows 실행은 아직 하지 않았습니다. Worker 번들은 비압축 약 36.2MiB, gzip 약 5.1MiB입니다. [공식 2026-09-04 변경](https://developers.cloudflare.com/changelog/post/2026-09-04-increased-worker-size-limit/)의 Free/Paid 공통 비압축 64MiB 제한 안에 있습니다. 크기 때문에 유료 플랜을 요구하지 않으며 CPU·시작 시간·사용량은 원격 시험에서 별도로 확인합니다.

## 버전과 배포

`engineVersion`은 게임 규칙·콘텐츠·선언한 프로토콜 버전으로만 계산합니다. `serverBuild`는 서버 구현과 실제 규칙 버전을 함께 묶어 배포 검증 결과가 다른 코드에 재사용되지 않게 합니다. 화면 호환 차단에는 사용하지 않습니다. 기존 운영 fingerprint는 정확히 같은 규칙 해시에만 연결해 기존 화면을 막지 않습니다. 임의의 과거 버전을 허용하지 않습니다. 서버의 행동 의미나 필수 프로토콜이 바뀌면 `server/protocol.json` 버전을 올려야 합니다.

전체 응답 감소 기능 때문에 UI 업데이트는 처음에 한 번 필요합니다. 이후 Worker 성능 수정은 Pages를 차단하거나 7GB 파일 묶음을 만들 필요가 없습니다. Windows 실행기·독립 성능시험·배포 gate와 계정별 롤백 절차는 [운영 안내](server-operations-ko.md)에 정리했습니다.
