# 서버 저장과 화면 진행 계약 — v0.13.49

검토 기준은 최신 main `d8fecb643bb8e7b955eba2b8ee3b3aeb0358019c`이며, 작업 브랜치는 `fix/nonblocking-gameplay-20260927`이다. 화면은 서버의 확정 결과를 표시하며, 클라이언트가 만든 세이브나 보상·난수 결과를 서버에 업로드하지 않는다.

## 확인된 원인과 수정

- 브라우저만 불러오던 `presentation.js`에는 실제 전투 기록을 보강하는 Runtime 훅도 있었다. 서버 빌드에서 빠져 대상 ID, HP 전후 값, 라운드·행동 번호가 없는 응답을 만들었다. 같은 이름의 적, 다단·광역 공격, 회복에 모두 영향을 주는 공통 문제다. 서버도 같은 훅을 같은 순서로 포함한다.
- 스토리 미리보기가 전역 `game`을 바꾼 뒤 요청의 화면 문맥을 캡처했다. 원래 문맥과 요청 ID를 먼저 기록하고, 성공 시 서버 상태로 확정한다. v0.13.49는 일반 대사/서술을 기존 Runtime에서 검증해 즉시 표시한다. 매 줄 Runtime을 재생성하던 약 0.27~0.45초의 동기 작업을 없앴다. 읽기 명령을 표시 전에 계정별 localStorage 저널에 기록하고, 0.9초 휴지 또는 최대 4초마다 묶어 전송한다. 진행 중인 체크포인트 응답 위에 나머지 읽기를 재적용하여 화면이 뒤로 돌아가지 않는다. 선택 전에 미전송 읽기와 선택을 한 트랜잭션으로 확정한다. 기존 체크포인트가 전송 중이면 먼저 확정한 뒤 선택을 보낸다.
- 마지막 메뉴 이름만으로는 중간 상점 이탈을 복원할 수 없었다. 다음 실제 행동에 순서가 있는 메뉴 기록을 포함한다. 서버가 각 이동을 검증하며, 정확히 같은 상태로 돌아온 반복 이동만 제거한다.
- 같은 세이브의 매 응답마다 Runtime 전체를 재생성하고 화면 복원을 실행했다. 콘텐츠 인덱스를 재사용하되 세이브 전체 검증은 유지한다. 새 여정·재접속에는 전체 복원을 수행하고, 일반 응답은 낚시 입력·표시 상태를 초기화하지 않는다.
- 작업 시작 응답과 작업 타이머를 이어서 기다리는 체감을 줄였다. 클릭 즉시 실제 활동 진행 게이지를 표시한다. 서버 작업 시계는 클라이언트 시각을 신뢰하지 않고 Worker 요청 도착부터 시작하여 인증/DB 처리 시간도 포함한다. 응답 시 서버 `startedAt`의 남은 시간으로 인계한다. 네트워크 전송 지연까지 없애는 계약은 아니며 서버 확정 전에는 보상을 지급하지 않는다. 서버 시간 헤더로 기기 시차를 보정하되 느린 응답마다 시계를 뒤로 밀지 않는다.
- 94% 상한을 없앴다. 이동 연출 시간이 지나도 응답이 없으면 부정확한 백분율 대신 확인 중 표시를 유지한다. 일반 변경은 화면 가운데 작업별 안내를 한 번만 표시한다(장착 중…, 편성 변경 중…, 보상 받는 중…). 빠른 응답에는 안내를 띄우지 않고, 중복된 우측 하단 안내는 제거했다. 전투는 기다리는 동안 준비 자세를 계속 움직이고 기존 전투 DOM을 유지하다가 서버 확정 타격을 재생한다. 응답 헤더뿐 아니라 본문 읽기까지 20초 제한을 적용한다.

- 자유행동 화면 안내가 전투까지 남아 조작부를 가리거나 화면을 스크롤하던 문제도 수정했다. 전투·준비 중에는 숨기고 이후 같은 안내 단계로 돌아간다.

## 행동별 저장 경계

| 행동 | 처리와 저장 시점 | 화면 처리 |
| --- | --- | --- |
| MENU, 설정·설명·장비 비교 | MENU 자체는 서버 요청·리비전 증가 없음. 대사 저장 중에도 즉시 열리며, 응답 후에도 현재 메뉴를 유지한다. 문맥 변화는 다음 실제 행동에 포함. 장비 비교는 읽기 전용 | 즉시 표시 |
| 일반 대사·서술 읽기 | 명시적 효과가 없는 읽기만 최대 64개 명령의 체크포인트. 서버도 같은 검증기를 사용하고 순서·루트·개인 이야기 문맥을 검증 | 즉시 읽기. 응답 유실/새로고침에도 계정별 저널 복구 |
| 선택·이름·효과 있는 대사·장 진입 | 앞선 미확정 읽기까지 서버에서 검증하고 진행·비용·보상을 원자적으로 확정 | 확정 전 추가 변경 방지 |
| 이동·장소 진입·대기·휴식 | 위치, 시간, 입장 조건, 조우 등 결과를 한 번에 확정 | 연출과 요청을 동시에 시작 |
| 보상·구매·판매·제작·강화 | 비용·아이템·완료 표시를 동일 트랜잭션으로 확정 | 확정 후 결과·획득 표시 |
| 편성·장비·전술·아이템 사용 | 실제 변경은 즉시 저장. 메뉴를 열기만 하면 저장하지 않음 | 현재 작업 화면 유지 |
| 전투 준비·시작·각 행동·종료 | 행동 순서, 모든 행위자 HP·상태·난수, 승패·보상을 함께 확정 | 첫 직접 입력 보장. 확정된 로그로 연출. 재생 중 과거 화면을 보여도 저장 대상은 확정 상태 |
| 생활·현장 작업 시작 | 작업 ID, 서버 시작 시각, 자원/미끼 소비를 즉시 확정 | 작업 진행 게이지와 시작 통신을 동시에 시작 |
| 생활·현장 작업 완료·취소 | 서버 경과 시간·입력 검증 후 보상 또는 취소를 확정 | 동일 작업 중복 완료 금지 |
| 새 행동 종류 | MENU 외에는 기본적으로 즉시 서버 저장 | 명시적인 읽기 전용 분류 없이는 저장을 생략하지 않음 |

보류 요청은 계정별로 요청 ID·기준 리비전·문맥·인자를 기기에 먼저 기록한다. 서버는 리비전 조건부 갱신, 영수증, 직전 세이브 백업을 함께 기록한다. 응답 유실 후 같은 ID로 확인하며 보상을 다시 지급하지 않는다. 다른 행동으로 보류 요청을 덮어쓰지 않는다. 재접속은 보류 요청 확인 → 읽기 저널 확정 → 남아 있는 전투 패배 처리 → 복원 순서다. 페이지 이탈/탭 숨김에서도 keepalive로 읽기 체크포인트 전송을 시도하고, 완료하지 못한 명령은 다음 접속에서 복구한다. 다른 기기가 이미 앞서 진행한 경우 오래된 미전송 읽기로 최신 서버 기록을 덮지 않는다. 화면 메뉴는 새로고침 시 서버의 마지막 확정 문맥으로 돌아가도 된다.

## 실행 검증

`npm test`는 실제 생성된 Worker 엔진, 메모리 SQLite로 구현한 D1 계약, 현재 콘텐츠 회귀검증을 실행한다. `npm run test:browser`는 실제 HTML/JS UI를 실행하고 API 호출만 동일 Worker/SQLite로 연결한다. production은 `npm run build` 후 `CRPG_TEST_DIST=1 npm run test:browser`로 다시 검사한다.

브라우저 검증은 다음을 서버의 저장 행과 직접 대조한다: 서버 응답 전 5개 대사 연속 읽기/2회 체크포인트, 읽기 응답 2회 유실/새로고침 단일 확정, 선택과 읽기 원자적 저장, MENU 요청 0건, 두 번의 응답 유실 후 단일 커밋, 요청 도착 0.5초 지연/응답 1.8초 지연/5분 기기 시차에서 응답 전부터 생활 진행 표시, 생활/현장 작업 완료, 가운데 장착 안내와 실제 장비 저장, 지연된 이동의 진행 표시, 주인공 첫 차례, 실제 표시 HP, 새로고침 전투 패배. 서버 검증은 중간 장소 이탈, 불가능한 메뉴 경로의 원자적 거부, 편성·장비 재접속 유지도 포함한다.

카탈로그 검사는 캐릭터 119종·적 222종의 카드 528개를 순회한다. 실행 가능한 228개에서 대상 식별·HP 전후·행동 프레임 계약을 검사하고, 나머지 300개는 별도 기록한다(미구현 전용 효과 281개, 페이즈·체력·강화 등 조건 제한 19개). 이는 모든 미구현 콘텐츠의 완성이나 모든 캐릭터의 밸런스를 보증하는 검사가 아니다. 보스·나선비경·몬드와 리월 전체 경로는 별도 기존 실행 테스트로 검증한다.

구세이브 검증은 실제 v0.13.43 엔진에서 만든 두 루트 × 대화/출발/전투/작업 8종을 현재 엔진으로 복원한다. 오래된 `test_life_v010`, `test_flow`, `test_party`는 현행 모듈/진행 조건 이전의 실행기라 초기 조사에서 실패했으며 release gate에 포함하지 않았다. 과거 외부 저장소 커밋을 요구하는 `test_save_v013` 역시 현 저장소에서 재현할 수 없다. 해당 테스트 기대값을 바꿔 통과시키지 않았다. `test_save_revision`은 누락된 실제 선행 모듈 로딩만 복구하여 기존 단언 그대로 실행한다.

## 배포 절차와 남은 운영 조건

1. 브랜치/PR에서 소스·서버 회귀검증 → 소스 UI 검증 → production build → production UI 검증을 통과한다.
2. CI가 해당 SHA의 `crpg-production-*`, `crpg-evidence-*` artifact를 보관한다. 빌드된 dist를 main에 커밋하는 단계와 `contents: write` 권한은 제거했다.
3. GitHub Pages Source는 v0.13.48 배포 때 이미 **GitHub Actions**로 전환했다. branch 기반 자동 배포로 되돌리지 않는다.
4. 권한 있는 Cloudflare 환경에서 이 브랜치의 v0.13.49 Worker를 배포한다. D1 스키마/운영 세이브를 삭제하거나 재생성하지 않는다. `server/wrangler.jsonc`의 build가 공통 엔진을 생성한다. 서버와 클라이언트의 버전이 잠시 다른 동안은 기존 버전 게이트가 행동을 보류하므로 두 배포를 같은 배포 창에서 진행한다.
5. 최종 검증된 변경을 main에 한 번 반영한 뒤 workflow_dispatch의 publish를 선택한다. 운영 Worker `/health`의 버전·설정 확인이 성공해야 Pages 단계가 열린다.
6. 전체 기존 사이트를 checkout하여 게임 외 공개 파일을 보존하고 검증된 dist만 덮은 Pages artifact를 배포한다. 기존 Pages artifact 자체가 약 7.2GB이므로 게임 89MB만 배포해 다른 이미지 경로를 지우면 안 된다.

v0.13.48은 Actions run `36316683441`에서 실제 게시 완료했다(main `d8fecb6`). v0.13.49의 게시 여부는 이후 Actions 실행과 Worker health/release.json을 확인한다. 이 환경의 Cloudflare 대시보드는 인증 확인 화면에 막혀 있으며, 사용자가 로컬 Wrangler 로그인으로 서버 ZIP을 배포하는 경로가 확인되어 있다. 서버 반영 전에는 새 클라이언트를 게시하지 않는다.
