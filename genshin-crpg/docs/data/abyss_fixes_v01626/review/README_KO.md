# 0.16.26 독립 수정 검토

최종 4개 제품 소스 기준 독립 계약 **13개 검사 묶음 전부 통과**, 별도 시작 경로 **39쌍 전부 통과**했다. 이번 수정 대상에서 새 회귀 오류를 발견하지 않았다. 옛 숨은 훈련 API의 별도 잔존 문제는 아래에 구분했다.

이 검토는 나선비경 중간 방의 주인공 전투불능 판정, 최초 행동 순서, 방 사이 아이템 허용 규칙을 확인한다. 전체 게임 난이도·모든 조합·자연 획득·48명 육성 완주를 검증했다는 의미가 아니다. 종려·진 관련 12층 요구 조건과 층별 적 구성·스펙·제한 라운드는 변경하지 않았다.

## 별도 시작 경로: 39쌍

원자료는 `STARTUP_ORIGINS.json`, 재실행 코드는 `startup_origins.cjs`다. 실제 첫 `newRound` 안의 `combatStat`와 `die(10)`를 결과 변경 없이 관찰했다. 각 배우의 **원래 난수 자체**를 포착하고 최종 점수가 **실제 최종 SPD + 그 난수**인지 정확히 검사했다. 단순히 차이가 0~9 범위라는 검사로 끝내지 않았다.

| 경로 | 전후 비교 사례 |
|---|---:|
| 일반·의뢰 조우, 실제 해시로 선택된 SWIFT, 관리자 SPD 1·88·1000, 속도 음식 | 5 |
| 돌파·특성·경험치 비경의 낮은 단계와 높은 단계 | 9 |
| 몬드·리월 계시의 꽃 각각 전 5단계 | 10 |
| 필드보스 9종과 반복 일일 보스 4종 | 13 |
| 이세계인 이야기 드발린 | 1 |
| 실제 이벤트 입력이 있는 공동 토벌 입장 | 1 |
| 합계 | **39** |

모든 경우 기동 진형을 사용했다. 261개 행동 순서 항목 중 적은 105개다. 배우 전체 데이터·원래 PRNG·원래 난수·`first` 표시가 전후 같고, 주인공 선두·그 뒤의 정렬·`opening.initialOrder`가 일치했다. 일반 `startBattle`가 직접 반환한 순서도 최종 `combatOrderView`와 같았다. 관리자 프로필이 있는 옛 저장은 같은 프로필로 재생성해 전체 전투 데이터가 그대로인지 검사했다.

비경·지맥·반복 보스·공동 토벌은 기존 공개 행동을 통해 입장했다. 일반 조우와 이야기 드발린은 기존 `startBattle`에 유효한 전투 종류·이야기 상태·편성을 넣어 시작했다. 일반 의뢰 사례는 실제 의뢰 연쇄 완주를 검증한 것이 아니라 `QUEST:` 시작 경로 검사다. 검사용 계정은 정상 규칙에 맞는 레벨·돌파·소유·접근 플래그·기본 특성을 준비했으며 장비와 성유물은 넣지 않았다. 적 수치·난수·공격·회복·전투 결과를 바꾸지 않았다.

물의 정령의 최초 물 형상 2개는 기존 설계대로 첫 순서가 만들어진 뒤 등장하여 그 순서에 들어 있지 않았다. 이들을 첫 라운드의 이미 존재하는 항목으로 세지 않았다. 전후 생성·수치·대기 정책은 동일했다.

## 연결 시스템 영향

`app_abyss.js`는 `NEXT`일 때만 다음 방 준비 버튼을, `CLEARED`일 때만 층 정복을 표시한다. 신규 `DOWNED`는 기존 실패 표시를 사용하며 진행 중인 층이 없으므로 휴식·다음 방 경로가 열리지 않는다. 이는 코드 경로와 상태/API 검사이며 휴대폰 브라우저의 시각 검사 결과는 아니다.

임무 승수는 실제로 그 방의 적을 처치한 경우를 집계하는 기존 규칙을 유지한다. 층 정복이 없어도 방 승리 1회는 유지하지만, 새로운 정복 기록·각인·정복 보상을 생성하지 않는다. 업적의 나선 정복은 보상 수령 기록, 운영 서버 순위는 `abyss.clears`를 사용하므로 중간 방 `DOWNED`로 새로운 층 정복 업적이나 순위를 얻지 않는다.

생활 작업 중 채집·사냥의 조우는 `lifeEncounter → rollEncounter → startBattle(..., 'RANDOM')` 공통 경로를 사용하는 것을 코드로 확인했다. 생활 미니게임을 끝까지 플레이한 검사는 아니며 일반 시작 경로 검사 결과만 연결된다. 나선과 공동 토벌은 공유 성장 튜닝의 예외를 그대로 유지한다. 공동 토벌 적의 HP와 타격 집계 규칙도 전후 동일하다.

## 별도로 남긴 기존 숨은 훈련 API

`startTutorialDrill()` / `TUTORIAL_DRILL`은 실제 이동·이야기 튜토리얼과 별개인 옛 훈련 API다. 앱 진입 호출은 검색에서 발견되지 않았지만 API 자체는 아직 실행 가능하다. 이 함수는 `startBattle` 반환 뒤 적 SPD를 20으로 다시 지정한다. 이번 수정 전후 모두 첫 적 점수가 64·65로 유지되어 최종 SPD와 44·45 차이가 났고, 훈련 영수증도 사후 변경과 일치하지 않았다.

재현은 `OPTIONAL_LEGACY_DRILL.json`과 `legacy_drill_probe.cjs`에 보존했다. 이 기존 숨은 경로는 최종 4소스 수정 범위에 넣지 않았다. 따라서 **모든 옛 숨은 API까지 첫 순서를 해결했다**고 인수인계하면 안 된다. 후속 수정 시에는 훈련의 사후 수치 지정 직전·직후 실제 SPD 차이로 순서 점수를 보정하고 주인공 선두·`initialOrder`·반환 순서를 함께 맞춰야 한다. 훈련 내용이나 전투 스펙을 새로 설계할 필요는 없다.

```sh

node --expose-gc --max-old-space-size=768 docs/data/abyss_fixes_v01626/review/startup_origins.cjs
node docs/data/abyss_fixes_v01626/review/legacy_drill_probe.cjs
```

`INDEPENDENT_REVIEW_FINAL2.json`과 `independent_review_final2.cjs`는 성장·관리자 보정이 추가되기 전 중간 2소스 기록이다. 최종 증거나 최종 통과 수에 합산하지 않는다. 최종 증거는 이름에 FINAL2가 없는 두 JSON이다.

실제 전투를 완주한 별도 전후 21쌍, 42회·87방 기록은 `../native/README_KO.md`와 `../native/comparison.json`을 참조한다. 여기의 시작/정산 검사 수와 실제 완주 실행 수를 합산해 승률이나 전투 횟수를 만들면 안 된다. 그 원자료의 최종 4소스 표본에서는 실제 주인공 KO 뒤 잘못 열린 `NEXT` 13건이 0건이 되었고, 기존에 주인공 KO 없이 정복한 6개 표본은 유지되었다. 이는 표본 결과이며 모든 조합의 정복 보장을 의미하지 않는다.
