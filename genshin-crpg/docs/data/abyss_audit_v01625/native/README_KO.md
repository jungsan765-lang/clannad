# 0.16.25 나선비경 실제 전투 감사

대상은 배포 커밋 `46190377b713e6218e66b26bc4292f18fb5a348d`의 전투 코드다. 제품 코드·수치·UI·콘텐츠·운영 DB는 변경하지 않았다. 아래는 특정 편성과 준비 조건을 공개 행동으로 실행한 진단 결과이며, 전체 유저의 승률 추정은 아니다.

**확인된 결론:** 조사한 5성 명함 편성이 준비 없이 최종층을 안정적으로 통과하는 상태는 아니다. 장비·특성·음식·편성·동료 행동 지침의 차이는 실제 결과에 반영된다. 다만 현재 나선비경을 “필요한 준비를 하면 공략으로 정상 완주하는 균형”이라고 최종 승인하기에는 두 가지 큰 문제가 남는다. 12층은 특정 캐릭터와 장비 조건을 충족하지 않으면 공격을 무효화하며, 주인공이 쓰러진 방도 승리 정산에서 무료 부활해 다음 방으로 넘어갈 수 있다. 이 때문에 `CLEARED`만 세면 준비 효과와 정상 완주를 과장한다.

## 공식 범위와 결과

공식 묶음은 아래 여섯 개뿐이다. 모든 조건은 전원 Lv60, 합법 돌파 단계와 특성 상한, 공개 장비 장착·운명의 자리 해금·입장·전투 행동을 사용했다. 각 케이스의 전투 시드는 `717 / 4242 / 9031`이다.

| 공식 묶음 | 실행 | 3방 완주 | 전투 정산 전 KO 없는 완주 |
|---|---:|---:|---:|
| `floor12_preparation` | 42 | 20 | 13 |
| `counter_preparation` | 33 | 10 | 2 |
| `roles_preparation` | 9 | 4 | 3 |
| `fixed_preparation` | 18 | 3 | 2 |
| `release_floor10_11` | 36 | 9 | 0 |
| `last_pyro` | 9 | 2 | 1 |
| 합계 | **147** | **48** | **21** |

실제 전투 시작은 310방이다. 최종 결과는 완주 48, 원래 제한 턴에 따른 시간 초과 69, 패배 30이다. 이 공식 범위에서 입장 거절, 12층 준비 판정 미달, 진단용 80회 입력 제한 도달, 실행 예외는 각각 0이다. 준비 미달 10·11층의 전투 중 무효화는 입장 거절과 별개다. `fixed_preparation`의 시드717은 이전 준비 비교의 기준행을 일부 반복하므로, **147회 실행을 147개 독립 표본이나 고유 승률 시험으로 해석하지 않는다.**

정상 완주는 `state === CLEARED`이면서 세 방 모두 `room.ko`가 비어 있는 경우다. 완주 48회 중 27회는 하나 이상의 방에서 실제 KO가 있었다. 승리 정산 후의 `finalKo`, 체력 합계만 읽으면 안 된다.

## 12층 준비 차이

기준 편성은 이세계인 주인공 + 종려·다이루크·진이다. 동료 세 명은 모두 5성 명함이고, 전원 Lv60·특성10·최대 +12 장비·조건을 충족하는 품질90% 이상 성유물 +5를 갖췄다. 연계 진형(`DOUBLE_LINE`), 동료 지침은 종려 지원 우선 / 다이루크 연계 우선 / 진 공격 우선이다. 주인공은 공개 방어를 반복하고 동료는 기존 AI로 행동한다.

같은 시드끼리는 같은 장비와 자연 성유물 수치를 쓴다. 서로 다른 세 시드에서는 자연 성유물 수치도 달라진다. 아래에서 “음식 3종”은 선도장·비옥야채쌈·만족샐러드이며, 각 방 시작에 살아 있는 네 명에게 먹인다. “회복”은 방 사이에서 체력이 75% 미만일 때 실제 회복 음식을 먹이는 조건이다.

| 조건 | 상태상 완주 / 3 | KO 없는 완주 / 3 | KO 없는 완주의 실제 소비 |
|---|---:|---:|---|
| 음식 없음 | 1 | 0 | 없음; 유일한 완주도 주인공 KO 포함 |
| 회복 음식만 | 0 | 0 | — |
| 선도장만 | 1 | 0 | — |
| 선도장 + 회복 | 1 | 1 | 선도장12 + 회복2 = **14개** |
| 선도장·비옥야채쌈 + 회복 | 2 | 0 | 두 완주 모두 마지막 방 주인공 KO |
| 공격 음식 3종 + 회복 | 2 | 2 | 공격36 + 회복1~2 = **37~38개** |
| 3종 + 어부토스트 + 회복 | 2 | 2 | 버프48 + 회복1~2 = **49~50개** |
| 4종 + 크림스튜 + 회복 | 2 | 2 | 버프60 + 회복1~2 = **61~62개** |
| 제작 무기 +12, 음식5종 + 회복 | 1 | 0 | 완주에도 주인공 KO 포함 |
| 동료 세 명 모두 5성 1돌, 선도장 + 회복 | 1 | 1 | 14개 |
| 동료 세 명 모두 5성 2돌, 선도장 + 회복 | 2 | 2 | 13~14개 |
| 동료 세 명 모두 5성 풀돌, 선도장 + 회복 | 3 | 3 | 선도장12; 회복 음식 소비 0 |

명함의 음식3종·회복 완주는 시드717에서 32라운드, 시드4242에서 26라운드였다. 시드9031은 음식5종까지 추가해도 첫 방 제한 12라운드에 걸렸다. 방어·속도 음식을 더 먹였다는 사실만으로 이 표본의 화력 문제를 해결하지 못했다. **버프 음식60개는 필수 최소 준비량이 아니다.** 단일 선도장·회복으로 정상 완주한 조건도 있으며, 3종에 방어·속도 음식을 추가한 비교는 정상 완주 수를 늘리지 않았다.

투자 비교의 풀돌은 **종려·다이루크·진 모두 풀돌**이다. 한 명 풀돌이나 5성 명함의 결과로 축소해 표현하지 않는다. 이 조건은 실제 운명의 자리 공개 해금을 거쳤으며, 특성 상승도 제품 구현대로 적용됐다.

### 장비와 전투 난수 분리

`fixed_preparation` 18회는 모든 조건에서 성유물·초기 육성 생성 시드를717로 고정한 뒤 전투 시드만 세 가지로 바꿨다. 명함 기준 단일 선도장·회복은 정상 완주0/3, 음식3종·회복은1/3, 음식5종·회복도1/3이었다. 이 표본에서는 성유물 차이 외에 실제 전투 난수에 따른 결과 차이도 있었다. 이를 전체 플레이의 무작위 실패율로 확대하지 않는다.

### 다른 불 원소 편성

종려·진을 명함으로 고정하고 불 원소 동료를 바꾼 마지막 9회도 같은 방어 정책을 썼다.

| 불 원소 동료 | 준비 | 상태상 완주 / 3 | KO 없는 완주 / 3 |
|---|---|---:|---:|
| 호두 명함 | 최대 장비, 음식 없음 | 0 | 0 |
| 호두 명함 | 최대 장비, 음식3종 + 회복 | 0 | 0 |
| 향릉 풀돌 | 최대 장비, 음식3종 + 회복 | 2 | 1 |

호두 음식 조건은 시드4242에서 세 번째 방,9031에서 두 번째 방의 시간 제한까지 진행했다. 향릉 풀돌의 정상 완주는 시드4242,31라운드·음식40개·최종 파티 체력83.0%다. 시드9031의 상태상 완주는 두 번째 방 주인공 KO 후 무료 부활을 포함하므로 정상 완주로 세지 않았다. 이 조사는 모든 가능한 편성·수동 정책의 최적해를 찾은 것이 아니다.

## 10·11층도 같은 문제를 분리했다

`release_floor10_11`의 기본 수동 정책은 주인공이 사용 가능한 원소전투 스킬, 원소폭발, 공격을 선택하고, 체력이30% 아래로 내려가면 방어하는 `E_FIRST`다. 앞서 말한 12층 방어 반복 결과와 섞어 비교하지 않는다.

- 10층 모나·각청·설탕 명함은 최대 장비와 선도장·회복을 갖춰도 완주0/3이었다. 바바라·리사·설탕 명함도0/3, 같은 4성 세 명 모두 풀돌은2/3 상태상 완주했으나 두 완주 모두 주인공 KO를 포함했다.
- 별도 `GUARD`·음식3종·회복 조건에서는 바바라·리사·설탕 풀돌이 **2/3 KO 없이 완주**했다. 같은 편성 명함은0/3이었다. 따라서 기본 정책 실패만으로 해당 층의 모든 수동 공략이 불가능하다고 판단하지 않는다.
- 11층 호두·감우·응광 명함은 선도장·회복 조건에서3/3 상태상 완주했으나 **모두 주인공 KO 포함**이었다. 방어 반복·음식3종 조건의3/3 완주 역시 같은 문제가 있었다.
- 11층 향릉·케이아·응광 명함은0/3, 세 명 풀돌은2/3 상태상 완주했으나 KO 없는 완주는 없었다. 보호·치유를 기대한 노엘 대체 편성도 방어 반복 표본에서 화력 시간 제한을 해결하지 못했다.
- 성유물과 전용 무기 없이 제작 장비 +6으로 시작한 10·11층의 여섯 조건은 모두 패배했다. 이 결과에는 해당 층 장비·원소 조건에 따른 공격 무효화가 포함되므로, 순수 생존력 차이만으로 설명하지 않는다.

## 판정을 막는 문제와 한계

1. **12층은 특정 캐릭터를 강제한다.** `abyssMasteryReady()`는 종려·진·불 원소 동료, 전원 Lv60, 무기·방어구·장신구 +12 및 상한12, 성유물 품질900 이상·강화5, 역할별 성유물 수치까지 검사한다. 미달이면 전투에 들어가도 피해가 무효화된다. 4성 풀돌이나 다른 5성 명함을 잘 준비한 편성의 일반적인 최종층 공략을 입증하는 구조가 아니다. 이 문서의 공식 12층 실전은 모두 그 준비 판정을 통과했으며, 미달을 실전 화력 부족으로 계산하지 않았다.
2. **주인공 KO 후 다음 방 진입 오류가 있다.** native 종료 직전 HP0과 승리 정산 후 HP10%가 달라지는 경로가 있다. 공식 실전에서 실제 KO 이후 양수 체력이 되는 기록은96건이었다. 이는 이벤트 수이며96명의 별개 캐릭터나96회의 독립 완주가 아니다. 해당 코드 경로·분리 계약은 메커니즘 감사 담당이 재현했다. 이 원장은 `room.native.actors`, `room.ko`, `room.nativeDownedPersistentRevived`, `room.after`를 함께 보존한다.
3. **첫 라운드 적 행동 순서가 최종 속도와 다르다.** 12층 적의 초기 최종 속도50과 달리 첫 순서 점수에는 템플릿 속도28이 남아 있고 다음 라운드는 최종 속도를 쓴다. 제품을 고치지 않고 실제 배포본 그대로 측정했으므로, 수정 후 첫 라운드 피격·KO·소비량은 다시 재현해야 한다.
4. **방어 반복 + 동료 AI의 승리는 세밀한 수동 공략 필수의 증명이 아니다.** `COUNTER`의 매3라운드 공격·자기 치유품 사용, 역할 지침 변형도 비교했지만 전체 최적 정책을 탐색하지 않았다. 치유품은 실제 `COMBAT ITEM:*`으로 소비됐고, 음식과 별도 집계했다. 치유품을 지급만 하고 “사용했다”고 세지 않았다.
5. **소유·강화·이전 층 기록은 진단용으로 지급했다.** 장비 수치는 제품의 장비·성유물 함수로 계산했지만, 이를 실제 신규 계정의 준비 시간이나 수급 가능성을 입증한 자료로 읽으면 안 된다. 준비 비용·수급 확률은 별도 공급 감사의 범위다.

## 정확한 실행 조건

- 주인공은 `ROUTE_ISEKAI` 한 명만 공개 조작하고 동료 세 명은 기존 AI로 행동한다. 캐릭터 기본 수치·적 스펙·피해 함수를 바꾸지 않았다. 운영자 밸런스 프로필은 비어 있고 revision0, 시작 전투의 캐릭터 밸런스 revision은1이다.
- 장비 준비 `EXCLUSIVE`는 동료 전용 무기 +12, 실제 필드보스 방어구 `EQ_FB_ARMOR_JADE_BULWARK` +12, 장신구 +12를 장착한다. 주인공 무기는 제작 무기다. 10층은 별도 장신구 `EQ_LY_ACC_STARGAZER`,11층은 `EQ_LY_ACC_QINGXIN_SACHET`을 전원 장착한다. `CRAFT`는 동료 무기도 제작 무기 +12로 대체한다. `POOR`는 제작 장비 +6·성유물 없음이다.
- 성유물은 원래 `rollArtifact()`로 생성하고, 역할별 판정을 만족하는 **첫 자연 생성값**을 최대4000번 안에서 선택한다. 품질·부옵션을 직접 좋은 값으로 변경하지 않았다. 다만 강화 레벨5·장비 강화치·소유·비용 지급은 육성 완료 fixture이며 실제 강화·획득 과정을 플레이한 결과가 아니다. 각 캐릭터의 시도 횟수·원본 instance·계산된 강화 수치는 `artifactRolls`에 보존한다.
- 음식은 종류별12개 재고를 진단 계정에 지급하고 실제 공개 `USE_ITEM`으로 사용한다. 각 방 시작의 식사 조건은 케이스 안에서 동일하다. HP를 채우는 것은 층 시작 한 번뿐이며, 방 사이 무료 숙박·HP 초기화·아이템 부활을 넣지 않았다. 제품 자체의 승리 정산 부활은 위 오류로 따로 기록한다.
- 실제 시작 상태에 선도장 `STATUS_FOOD_FEAST`(공격12%·치명5), 비옥야채쌈 `STATUS_FOOD_ATK`(공격8%), 만족샐러드 `STATUS_FOOD_CRIT`(치명5), 어부토스트 `STATUS_FOOD_DEF`(방어8%), 크림스튜 `STATUS_FOOD_SPEED`(속도4)가 각기 다른 상태로 들어간다. 크림스튜를 방어 버프로 세지 않았다. 음식 보정은 status mods로 계산하므로 `initialActors.atk` 필드 자체가 음식만큼 증가해야 한다고 해석하지 않는다.
- `GUARD`는 항상 방어, `SAFE`는 HP85% 아래에서 방어, `COUNTER`는 매3라운드만 공격 정책을 쓰고 나머지는 방어한다. 의약품 조건은 매3라운드 HP75% 아래에서 사용할 수 있는 메디킷·포션·붕대 중 하나를 자기에게 쓴다. `E_FIRST`는 HP30% 아래에서 방어한다. 케이스 `spec.policy`가 정책의 기준이며, 없는 경우 `E_FIRST`다. raw 상단의 공통 설명은 이 기본 정책만 설명한다.
- 한 층은 **한 파티로 세 방**이다. 현재 CRPG 구현은 두 파티를 교대하는 방식이 아니다. 층 완주 후 동료 사용 표시가 남는다. 여기서는 각 층을 독립적으로 시험하기 위해 이전 층 완료 기록을 지급했으며, 한 시즌 전 층을 통과할 전체 캐릭터 보유·편성 비용은 증명하지 않는다.
- 방당 최대80번 주인공 입력과 원래 제한 라운드를 그대로 적용했다. 실제 측정에서 입력 제한을 인위적인 패배로 만든 경우는 없었다. 별 점수 시스템은 현재 구현에 없어 별 수를 생성하지 않았다.

## 원장과 재현

`official_summary.json`은 공식 묶음·케이스 집계, `official_rows.csv`는147행 표, `validation.json`은 원 입력과 스냅샷 검증 결과다. 각 묶음의 `native.json.gz`에 장비, 성유물, 실제 운명의 자리·특성, 첫 상태, 공개 입력, 종료 직전 전투 로그, KO, 정산 후 HP, 음식·전투 치료품 실제 소비를 보존했다. 원장 용량을 줄이기 위해 로그의 화면 출력용 `presentation*` 복제만 제거했다.

각 묶음은 당시 실행한 `runner.cjs`와 `runner.cjs.gz`를 보존한다. 실행 완료 후 공통 runner가 여러 번 확장됐으므로, **현재 `audit_native.cjs`를 옛 결과와 동일한 실행 파일이라고 주장하지 않는다.** 공식 묶음의 snapshot은 각각 그 묶음의 `input_manifest.json.runner`와 SHA256이 일치한다. 기본/진단 helper는 입력120개 제품 파일과 별개이므로 `MANIFEST.json`에도 해시를 남긴다. 이 helper는 감사 종료 시 `harness/`에 저장했으며, 원 묶음 입력 manifest가 처음부터 해당 helper까지 해시했다는 주장은 하지 않는다.

저장 runner와 현재 helper로 기존 명함·음식3종·회복 시드4242를 한 번 재실행해, CPU 실행시간 필드만 제외한 **전체 원장 행**이 원 측정과 일치함을 확인했다. 장비·성유물·공개 입력·전투 로그·KO·소비·HP를 포함한 원 행과 재실행 행의 정규화 SHA256을 `replay_validation.json`에 보존했다. 이 기존 조건 재현1회는 공식147회 합계에 추가하지 않았다.

재현은 해당 커밋의 별도 감사 체크아웃에서 QA DB를 사용해야 한다. DB SHA256은 `254c9294c7787b421f38c84b3ad8fed9f00c207a8ef74855868c0cda48dc0962`, 로더 fingerprint는 `aeb110f1cb71c11b2d515e71c1a8f24189463d09eb26fd9959afe10b576aadd1`이다. 운영 DB를 QA DB로 교체하지 않는다. QA 원본은 기존 `docs/data/balance_v01625/field/release_final/harness/qa_db.json.gz`이다.

예시: 저장된 묶음 runner는 하위 디렉터리에 있으므로 `--root`와 `--cases`를 반드시 명시한다. 임시 출력 경로를 사용해 기존 원장을 보존한다.

```bash
node --expose-gc --max-old-space-size=640 \
  "$REPO/docs/data/abyss_audit_v01625/native/floor12_preparation/runner.cjs" \
  --root "$REPO" \
  --cases "$REPO/docs/data/abyss_audit_v01625/native/final12_cases.json" \
  --seeds 717,4242,9031 --out /tmp/abyss-0.16.25-replay
```

`release_floor10_11`은 `cases.json`에서 원래 선택했던12개 ID만 실행한다. 정확한 선택 ID와 모든 묶음의 입력은 `validation.json.bundles`에 들어 있다. 다른 묶음은 해당 이름의 케이스 파일 전체를 실행한다. 집계 재검증은 다음 명령이다.

```bash
python "$REPO/docs/data/abyss_audit_v01625/native/summarize_native.py" --root "$REPO"
```

이 검증은 공식 여섯 묶음의 runner·케이스·시드·동결6파일·제품120파일·QA DB가 서로 일치하고 현재 파일도 그대로인지 검사한다. 파이썬 실행시간·native CPU 시간·gzip 컨테이너 메타데이터까지 동일해야 한다는 주장은 아니다.

`probe`, `strategy_probe`, `stack_probe`, 최초 `floors10_11`은 중간 탐색 자료로 공식 합계에서 제외했다. 최초10·11층은 실행 중 진단 runner가 확장돼 종료 시 기록된 runner 해시 문제가 있었고, 복원본을 시작 시 캡처본으로 포장하지 않았다. 같은36조건을 실제 저장 snapshot으로 다시 실행한 `release_floor10_11`을 공식으로 채택했다. 첫 마지막 불 원소 케이스 생성 실패도 `last_pyro_initial_failure.log`에 남겼으며 게임 전투 예외로 계산하지 않았다.

제품 오류 수정이나 밸런스 수치 변경 후에는 이 동결본의 정상 완주 수를 재사용하지 말고, 같은 준비·시드·정책으로 새 버전을 다시 실행해야 한다.
