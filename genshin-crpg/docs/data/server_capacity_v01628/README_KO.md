## 부하 측정 조건

Node v24.19.0, x64, 논리 CPU 9개인 격리 환경이다. 실제 VPS 하드웨어와 다른 환경이며 운영 계정·서버에 부하를 보내지 않았다. 클라이언트와 HTTP 서버는 별도 프로세스, SQLite는 임시 디스크 파일·WAL·synchronous FULL이다. 계정별 SSE 1개를 유지하고 동시 요청 8개로 계정 수 16/32/64, 행동 3회씩을 실행했다. 버전별 672행동, 두 버전 합계 1,344행동이다. 각 조건은 별도 서버/DB를 사용하며 기본 런타임 캐시 16개는 같다.

`menu`는 MENU/SYSTEM의 저장·HTTP 비교용 단순 명령이다. 실제 클라이언트 메뉴는 로컬에서 처리하는 경우가 있으므로 이용자 부하 대표치로 환산하지 않는다. `combat`은 실제 여행자/엠버/케이아/리사 Lv20와 얼음 나무 전투의 시작 후 방어 3회·동료 AI다. 진단용 소유/레벨/전투 상태를 준비했고 준비와 비밀번호 해싱 시간은 행동 측정에서 제외했다. 전투가 끝나면 메뉴로 돌아가는 도구 조건도 공개한다. 로그인 폭주·자연 계정 전체 전투·대형 거래시장·장시간 지속 부하는 미측정이다.

처리량은 클라이언트의 실제 요청 구간으로 계산한다. 원본 `elapsedMs`는 서버 stats가 반환하는 종료 후 GC까지 포함한 시간이다. 원본에서 클라이언트 구간은 `actions*1000/actionsPerSecond`로 복원 가능하다. 후속 재현 도구에는 혼동을 피하려고 `clientElapsedMs`를 별도 저장했다. RSS/heap은 명시적 GC 뒤, peakRss는 서버 프로세스 피크다. CPU 시간에는 종료 후 GC가 포함된다. 응답 bodyBytes는 TLS/헤더를 제외한다.

부하 도구의 `durableDigest`는 **SQLite에 저장한 공개 게임 상태와 영수증 필드**의 해시다. 6조건 모두 이전/이후가 같고, 모든 HTTP 변경분을 재구성해 SQLite 공개 상태와 대조했다. 전체 private DB 바이트 해시라고 부르지 않는다. private PRNG/processed 누출 차단·되돌리기는 별도 512조건, 실제 private 저장 전체 동등성은 런타임 테스트가 검사한다. 매 행동 영수증 1개·종료 시 잠금 0·열린 트랜잭션 0도 확인했다.

재현은 별도 작업 사본에서 의존성을 설치하고 `python3 tools/build_server.py` 뒤 실행한다.

```bash
node tools/benchmark_server_capacity_v01628.mjs --accounts=16,32,64 --rounds=3 --concurrency=8 --workloads=menu,combat --output=evidence/capacity-v01628/reproduced.json
python3 tools/check_server_capacity_v01628.py
```

도구는 설치 서버 URL을 받지 않고 로컬 임시 서버만 만든다. 기준판 재현은 같은 도구를 기준 커밋의 작업 사본으로 복사하고 그 기준판 엔진을 새로 빌드한다. 엔진과 서버 코드를 섞거나 원문 DB를 옛 로컬 DB로 대체하지 않는다. CPU 프로파일링·다른 검사와 동시에 부하 측정을 실행하지 않는다. 선택 옵션 `--heap-mib`는 별도 메모리 실험용이며 기본 성능 비교에서는 사용하지 않았다.

## 신규 검사와 기존 검사

신규 `test_runtime_capacity_v01628.cjs` 7항목은 공유를 끈 기준 생성 방식과 최종 방식의 설치 표·양쪽 경로 전체 이야기 그래프·계정 이름 표시·Lv1~60과 전 캐릭터 능력치·계정별 가변 상태·운영자 설정/DB 소유자 격리·실제 4인 전투 private 저장·원문 DB 보존을 비교한다. 콘텐츠만으로 생성되는 completionNodes는 양쪽 모두 생성 후 비교한다.

신규 `test_server_capacity_v01628.mjs` 7항목은 공개 패치 512조건, 설정 경계, SQL 캐시의 128개 상한과 최신 조회 값, 신규 PID 즉시 조회, 로그아웃 반영, 1회 정산/거절 복구, 미사용 캐시 정리와 저장 복원을 검사한다.

기존 24개를 포함한 최종 26프로그램은 모두 exit0다. 소셜·협동·성장·운영자 설정·읽기 체크포인트·저장 복구·엔진 식별·고정 SHA 적용 계약을 포함한다. 기존 부하 경계 검사의 동시 중복 100건(정산1/재생99), SSE와 외부 SQLite 잠금 복구도 유지한다. 프로그램 수, 그 안의 assertion 수, HTTP 행동 수를 서로 합치지 않는다. 전체 릴리스 등록에는 신규 2개를 추가했으나 전체 릴리스/클라이언트 전체 빌드/운영 VPS를 이번에 새로 실행했다고 쓰지 않는다. 배포 격리 프로그램은6항목 통과·전체 클라이언트 산출물을 요구하는1항목 생략이다. 최종 정적 콘텐츠5항목과 코드/설치기 구문·diff 검사도 통과했다.

## 공유 계약과 남은 한계

- 캐시 키는 immutable DB 소유자와 운영자 설정 판이다. 전체 Runtime·save·이름·선택·전투·가변 설치 표는 공유하지 않는다. 계정별 DB wrapper와 table registry도 유지한다.
- 전체 이야기 그래프는 현재 정적 컴파일 8개 wrapper를 포함한다. 개인 이야기 확장 테이블 설치와 플래그의 정적 부작용을 재현한다. 공유 노드 행은 freeze하며 표시를 위한 복사본을 사용한다. completionNodes는 콘텐츠만을 사용하는 메모다.
- 미래 이야기 컴파일러가 계정 flag/name/choice를 읽거나 노드 행을 변경한다면 이 캐시 계약을 다시 검토해야 한다. 새 사용자별 내용은 공유 그래프에 쓰지 않는다.
- SQL 캐시는 질의 객체만 재사용한다. 인증·로그아웃·제재·관리자 설정 조회 결과를 캐시하지 않는다.
- 런타임 캐시 기본16/미사용10분, 매분 정리라 해제는 대략10~11분이다. 인위적 최대128 확대·SSE500 확대·비밀번호 비용 감소는 하지 않았다.
- 노드 sqlite는 동기 방식이며 외부 writer의 기존 busy_timeout 5초는 이벤트 루프에 영향을 줄 수 있다. 기존 실패 후 복구 검사는 통과했지만 이 구조를 비동기/여러 서버로 바꾼 것은 아니다.
- 일반 Worker의 3인자 Runtime 생성 경로는 기본 동작을 유지한다. 이 결과를 Cloudflare Worker 성능 개선으로 주장하지 않는다.
- 실제 VPS 동시접속 한도·CPU/RAM·시장 거래량·1시간 이상 지속 부하는 미측정이다. 처리량 6.74배를 사용자 수 6.74배의 보장으로 바꾸지 않는다.
- 원문 DB·UI·assets와 0.16.27 성장/회복/전투/경제 숫자는 같다. 최적화 완료와 이전 밸런스의 모든 한계 해소는 별개다.
