## 2. 실행 전 준비와 증거 기록

1. 검사할 소스를 빌드하고 생성 시점의 커밋·DB 해시·클라이언트/서버 버전을 기록한다. 이전 `dist`가 남았으면 새 소스를 검사한 것으로 쓰지 않는다.
2. 로컬 UI 준비 도구를 `genshin-crpg` 디렉터리에서 실행한다. 도구의 생성 README와 `manifest.json`을 최종 fixture 이름·경로의 기준으로 사용한다.

   ```bash
   node tools/qa_fixture_generator.cjs --output /tmp/crpg-qa --game-dir dist --game-url http://127.0.0.1:4177/game/ --serve
   ```

3. 도구가 안내한 로컬 `/qa/`를 연다. 결과는 `fixtures/*.json`, `manifest.json`, `qa.html`, `qa-game.html`, `README.txt`다. 제품의 `dist`를 편집해 준비 상태를 심지 않는다.
4. 각 검사 전에 원래 fixture를 다시 선택해 초기 상태로 시작한다. 같은 저장에서 앞 검사의 소비·보상·선택이 다음 검사에 섞이지 않게 한다.
5. 결과마다 `항목 ID / 날짜 / 빌드·DB / fixture / 브라우저·OS / CSS 폭×높이 / 기기·DPR / 게임 글자 크기 / 브라우저 확대 / 입력 방식 / 절차 / 기대 / 실제 / 증거 / 판정`을 남긴다.

**로컬 도구의 경계:** 실제 제품 UI·런타임 자산을 동일 출처 iframe에서 불러오되, QA 전용 wrapper가 `app_revision`에 의해 덮인 `app.js`의 `loadState` 진입을 복원한다. 온라인 설정과 `app_online`을 제외하고 부팅 저장·서비스 워커를 막는다. 따라서 이 화면에서 성공해도 로그인·온라인 저장·서버 권한·서비스 워커 업데이트가 통과한 것은 아니다. 합성 상태의 레벨·아이템·개방 조건은 화면 재현을 위한 것으로 자연 성장 균형을 증명하지 않는다. 실제 사용자 세이브로 가져오지 않는다.

`--serve`의 기본 QA 서버 포트는 **4177**이며 `/qa/`와 기존 `dist`의 읽기 전용 `/game/`을 같은 출처에서 제공한다. 별도로 실행 중인 제품 확인용 **4173** 서버와 혼동하지 않는다. 시작 화면의 주소와 manifest를 증거에 함께 남긴다.

판정은 `PASS / FAIL / BLOCKED / NOT RUN` 중 하나다. 잠금·계정 부재·도구 제한은 이유를 적고 BLOCKED로 남긴다. 소스상 정상이라는 이유로 브라우저 행을 PASS로 바꾸지 않는다.

## 6. 서버로 보내는 양과 순간 멈춤 측정

P01 첫 로딩, P02 같은 화면 재방문, P03 대사·일반 행동 10회, P04 메뉴 왕복 10회, P05 거래 검색 변경, P06 편지 수령, P07 협동 한 차례, P08 유휴 60초를 구분한다. 로컬 UI 도구에는 온라인 모듈이 없으므로 P03 이후 HTTP 검사는 정상 온라인 클라이언트에서 한다.

| 측정 | 기록할 값 | 판정 방법 |
|---|---|---|
| 전송량 | endpoint별 요청 수, 요청 body 바이트, 실제 transfer bytes, decoded bytes, 압축, 캐시 여부 | decoded 크기를 실제 전송량이라고 쓰지 않는다. 메뉴만 바꿨는데 상태 변경 요청이 발생하는지 원인을 추적 |
| 지연 | 사용자 입력→반응, TTFB, 서버 처리, 응답 파싱/상태 설치/렌더, 50ms 이상 long task | 네트워크 대기와 메인 스레드 멈춤 분리. 동일 상태의 최초/반복 결과와 기기를 함께 기록 |
| 중복 | requestId, revision, HTTP/SSE 유발 횟수, 재시도 간격 | 같은 의도의 반복은 중복 결제·보상이 없어야 함. 정상 재연결과 무한 재시도 구분 |
| 복구 | offline/timeout/429/5xx 후 안내, 대기 해제, 재시도 결과 | 실패한 요청 때문에 무한 로딩·입력 잠금·이전 상태 고착이 남지 않음 |
| 누적 | 팝업 열고 닫기 20회 전후 리스너·DOM·힙 추세, 긴 세션 캐시/세션 기록 | 숫자 증가만으로 누수 단정하지 않고 해제·GC 후 잔존 및 반복 추세 확인 |

기존 감사의 data.js 실제 전송 약 4.02MB, decoded 약 23.09MB, 로컬 Node Runtime 복원 중앙값 535ms는 당시 환경의 관측치다. 이번 빌드나 한국 실사용 폰의 수치로 재사용하지 않는다. 합의된 성능 예산이 없으면 임의의 합격 숫자를 만들지 말고 반복 가능한 정체 구간·비정상 요청 증가를 결함 후보로 제출한다.

## 8. 한국어·그림·서사 검토 규칙

- 화면별로 `undefined/null/NaN`, 원시 노드·아이템 ID, TODO/임시/구현 예정/디버그 설명, 영문 내부 enum이 플레이어 문장에 나온 경우 위치와 원문을 기록한다. 단순 단어 검색 결과를 전부 결함 처리하지 않는다.
- 원신 고유 명사와 재료 이름은 한국 공식 게임/공식 자료의 같은 대상을 대조하고 출처·확인 날짜를 적는다. 익숙하지 않다는 이유로 임의 음역이나 다른 번역으로 바꾸지 않는다. 시스템 자체 용어와 원신 공식 용어를 구분한다.
- 그림은 파일 존재 외에 실제 화면의 화자·인물·장소와 대응하는지, 로딩 실패·잘림·과도한 여백·반복 기본 그림을 확인한다. 의도적인 텍스트 화면에 그림이 없다는 사실만으로 오류라 단정하지 않는다.
- 이야기 품질은 소개/인사, 서로 아는 관계, 인물별 지식과 감정, 행동의 동기, 목적→문제→해결의 인과, 사건 전후 시간·위치, 선택의 반응, 합류 과정·후속 관계를 한 장면씩 읽고 평가한다. 기술적 노드 완주와 서사 완성도는 다른 결과다.
- 개인·호감도 사건은 시작 버튼과 보상이 있다는 것만으로 이야기 존재를 인정하지 않는다. 만남의 이유, 서로의 반응, 사건을 거친 변화, 종료 후 관계의 연속성을 확인한다. 원고를 수정하기 전 문제 장면·기대 맥락·근거만 별도 제출한다.
- 공개 결과에는 줄거리·숨겨진 상자 위치·퍼즐 해답을 노출하지 않는다. 재현에 필요한 내부 식별자는 제한된 증거 파일에서만 다루고 화면 사진은 필요한 부분만 사용한다.

## 9. 진행 순서와 완료 게이트

1. 빌드/fixture 생성 검증과 기존 수정 회귀부터 확인한다. 생성 실패는 도구 실패로 기록하고 제품 버그와 구분한다.
2. F01~F12를 390px·1100px·글자100%로 한 번씩 실행해 막히는 화면을 먼저 찾는다.
3. V01~V04의 작은 폭·큰 글자·짧은 높이·폭 전환을 완료한다. 사진과 실제 좌표 클릭 증거를 모은다.
4. 정상 온라인 클라이언트+로컬 백엔드에서 O01~O12와 P01~P08을 수행한다. 재시작·응답 유실·경쟁은 이 단계에서 확인한다.
5. 실기기 V07 및 일반 PC 프레임 V05를 수행한다. 접근 가능한 테스트 계정으로 원격 배포의 같은 수정만 재확인한다.
6. 7절의 미포함 기능에 필요한 fixture/계정 조건을 마련해 기능군별로 확장한다. 서사는 한 루트·한 사건씩 별도 검토한다.
7. FAIL은 재현 조건·영향·근거·수정 전후 결과를 묶고, BLOCKED/NOT RUN은 남은 조건과 다음 행동을 적어 제출한다.

검사 중 확인되지 않은 결함을 임의로 고치거나, 사용자 데이터·보상량·난이도·스토리를 변경하지 않는다. 즉시 조치가 필요한 서비스 장애가 아니라면 먼저 결과를 보고한다. 수정 권한이 별도로 주어진 작업의 회귀도 같은 증거 구분을 유지한다.

최종 보고에는 **수행한 행 수 / 통과 / 실패 / 차단 / 미실시, 실제 사용 기기, 로컬·원격 구분, 수정 후 재검증 여부**를 반드시 적는다. “전부 정상”, “모든 루트 검토 완료”, “모바일 대응 완료”는 이 표에 미실시 범위가 남아 있는 동안 사용하지 않는다.
