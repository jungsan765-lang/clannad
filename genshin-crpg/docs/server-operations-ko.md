# 서버 구조 개선: 운영 반영과 복구

현재 운영에는 아무것도 적용하지 않았습니다. D1을 삭제하거나 새로 만드는 작업은 없습니다.

## 지금 사용자가 할 일

2026-09-30 시험기의 전체 상태 초기화가 Durable Objects 일일 무료 쓰기 한도를 초과했습니다. **기존 파일은 다시 실행하지 않습니다. 한국 시간 10월 1일 오전 9시 이후에 이번 사용량 제한 수정본을 사용합니다.** 원인과 로컬 쓰기 검증은 [사고·수정 기록](server-benchmark-quota-incident-ko.md)을 확인합니다.

1. 전달받은 성능시험 ZIP을 압축 해제합니다. Node.js 24와 Python 3.10 이상이 필요합니다.
2. 한국에서 `test-server.cmd`를 더블클릭합니다. Cloudflare 로그인 화면이 나오면 기존 운영 계정으로 로그인합니다.
3. 완료 후 생성되는 `latency-result.json`을 전달합니다. 실패하면 다시 실행하지 말고 `latency-partial.json`을 전달합니다. 비밀번호나 Cloudflare 토큰은 보내지 않습니다.

이 실행기는 `genshin-crpg-latency-test`라는 별도 Worker·D1·Durable Object만 만듭니다. 운영 DB ID를 거부하며 실제 사용자 세이브 대신 가짜 시험 세이브를 사용합니다. 시험 환경의 소액 사용료가 생길 수 있습니다. 결과 파일에는 비밀번호·세션 토큰을 넣지 않습니다. CMD 명령을 반복 입력할 필요가 없습니다.

한국 실측 통과와 실제 하루 행동량에 맞는 쓰기 사용량 검토를 마치기 전에는 최종 PR 및 운영 배포를 하지 않습니다. 목표는 따뜻한 상태의 MOVE/COMBAT HTTP 왕복 중앙값 150ms 이하, p95 300ms 이하입니다. p95는 100번 중 95번이 그 시간 안에 끝나는 기준입니다. 로그인·첫 이전·장시간 유휴 후 재시작은 별도로 봐야 합니다. 시험은 응답 다운로드를 포함하며 화면 렌더링·전투 연출 시간은 포함하지 않습니다.

## 검토 후 운영에 반영할 때

검증된 커밋으로 최종 PR 한 번을 만들어 병합합니다. 다음 항목을 사용자에게 보고한 뒤 승인된 최종본만 배포합니다.

- D1: `game_owners`, `game_checkpoints` 표와 이전 세이브 쓰기를 막는 트리거 추가. 기존 계정·세션·세이브·백업은 유지.
- Worker: 계정별 SQLite Durable Object 바인딩 추가. 새 접속부터 세이브를 안전하게 옮김. 인증·행동·저장 확인은 같은 계정 저장 공간에서 처리.
- Pages: 작은 응답과 새 세션 주소를 이해하는 UI를 처음에 한 번 업데이트. 이후 서버 성능만 바뀌면 Pages를 다시 올리지 않음.

`deploy-server.cmd`는 같은 serverBuild의 한국 시험 통과 파일이 없으면 중단합니다. 승인 문구 `DEPLOY`를 입력하면 추가 스키마 적용 → Worker 배포 → health 확인을 수행합니다. 기존 비밀번호 pepper와 운영자 설정은 유지합니다. Pages는 자동으로 배포하지 않습니다. 필요한 첫 UI 업데이트는 GitHub Actions의 `CRPG Verify and Publish Artifact`에서 `publish`를 켜고 한 번 실행합니다. 이 작업도 Worker의 게임 호환 버전을 확인하고 진행합니다.

이후 Worker 변경은 `CRPG Server Only` 검사를 사용합니다. 서버 구현만 변경한 PR은 대용량 Pages 빌드·업로드 경로를 실행하지 않습니다. Python 실행기는 Windows에서 `py -3`, `python`, `python3` 중 실제 사용 가능한 명령을 찾습니다. Wrangler를 직접 사용한다면 `genshin-crpg` 폴더에서 실행합니다.

## 이전 중 장애가 나면

한 계정의 이전 순서는 다음과 같습니다.

1. D1의 소유권 표로 이전 기록을 잠가, 구 Worker가 낡은 기록에 쓰지 못하게 합니다.
2. 원본 세이브·현재 남아 있는 receipt를 읽고 검증합니다. 원본은 그대로 남깁니다.
3. 계정 DO에 한 번의 SQLite 트랜잭션으로 복사하고 저장 완료를 확인합니다.
4. 활성화 표시를 남긴 후 행동을 허용합니다. 실패하면 같은 이전을 다시 시도합니다.

이미 활성화한 DO 데이터가 없어진 경우, 오래된 D1 원본을 자동으로 가져와 덮어쓰지 않고 중단합니다. 이 경우 DO의 복구 기능으로 원래 저장 공간을 복구해야 합니다. 압축 D1 체크포인트는 최대한 자주 만드는 추가 사본이며, 장애 동안 늦어질 수 있습니다. 최신 승인 행동을 잃어도 되는 자동 복구 원본으로 취급하지 않습니다.

## 롤백: 예전 Worker로 덮어쓰면 안 됩니다

계정별 `/ops/storage/rollback`은 운영자 세션만 허용합니다. 요청 본문은 `{ "accountId": "대상 계정 UUID" }`이며 POST입니다. `/ops/storage/status`, `/ops/storage/export`도 같은 인증·대상 형식을 사용합니다. export에는 서버 난수 상태가 포함되므로 사용자 공개 자료로 취급하지 않습니다. 비밀번호 해시·salt는 내보내지 않습니다.

계정 drain은 행동을 잠근 뒤 receipt와 밀린 로그아웃 취소 기록을 복사하고, 최신 세이브·revision과 D1 소유권을 한 트랜잭션으로 넘깁니다. 넘긴 기록을 다시 읽어 확인한 뒤 DO를 동결합니다. 복구된 계정은 같은 Worker에서 D1 경로로 연결됩니다. 중간 장애는 같은 drain을 다시 실행해 이어갑니다. 단순히 과거 세이브를 다시 덮어쓰는 방식이 아닙니다.

전체 롤백은 운영자가 다음 순서를 지킵니다.

1. `GAME_IMPORT_DISABLED=1`을 적용해 신규 이전을 막습니다. 이미 진행 중인 이전이 끝났는지 확인합니다. 실패한 미완료 이전은 원인을 복구하고 완료시킨 뒤 drain합니다.
2. D1 `game_owners WHERE owner='DO'` 목록의 모든 계정을 drain하고, 다시 조회해 0개인지 확인합니다. 계정별 상태와 넘긴 revision을 보관합니다.
3. 그 다음에만 backend를 D1으로 전환합니다. v2 토큰을 처리하는 이번 Worker를 유지합니다. 아주 오래된 Worker로 복귀하면 재로그인이 필요할 수 있습니다.
4. D1 원본과 DO namespace를 지우지 않습니다. 소유권·넘긴 revision·checksum 증거도 유지합니다.

이 전체 롤백은 운영 상태 확인이 필요한 작업입니다. 성능시험 실행기나 배포 실행기가 임의로 수행하지 않습니다. 운영자가 과거 revision으로 강제로 되돌리는 재해 복구는 승인된 행동을 취소할 수 있으므로 일반 배포 롤백과 구별해야 합니다.

## 저장 정책과 남는 비용

| 종류 | 정책 |
|---|---|
| 이동·전투·보상·상점·장비·생활/작업 시작과 완료 | DO에 결과·난수·revision·receipt·복구 정보 동기 저장 후 성공 응답 |
| 대사 읽기·기존 대화 선택 | 기존 클라이언트 기록 및 장면/행동 체크포인트 정책 유지. 한 줄마다 서버 저장하지 않음 |
| 단순 메뉴 열기 | 클라이언트에서 즉시 처리. 필요한 메뉴 문맥은 다음 서버 행동에 포함 |
| 랭킹·추가 D1 압축 사본 | DO에 먼저 확정한 후 보통 10초 단위로 합쳐 반영. 실패하면 재시도 |
| 초기 접속·불일치 복구·중복 요청 재조회 | 전체 세이브를 내려 정확한 기준을 복구 |

DO receipt는 오래된 응답 유실에도 같은 결과를 찾도록 유지하므로 행동 수에 따라 저장 사용량이 늘어납니다. DO의 최근 역방향 백업은 4개이고 기존 D1 백업도 보존합니다. 기존 D1에서 이미 삭제된 오래된 receipt는 되살릴 수 없습니다. D1 경로로 drain한 뒤에는 기존 D1 보존 정책이 적용됩니다. revision 검증으로 오래된 행동을 다시 실행하지 않는 보장은 유지됩니다.

랭킹에는 약간의 반영 지연이 생깁니다. 장시간 D1 장애 시 그 지연은 더 길어지지만 DO에서 승인한 게임 진행은 유지됩니다. 지역 힌트 `apac-ne`는 한국 배치를 보증하지 않습니다. 실측 목표를 못 맞추면 배치 위치·cold start·연결 경로를 추가로 조사한 뒤 반영합니다.
